# infra-example

[← Repository README](../README.md)

Two example **root configurations** built from `modules/`: `dev/web-demo` and `prod/web-demo`. The reviewer and the workflows treat
them like any other root; nothing in the platform depends on these names. Setup, branches, secrets and the pipeline are in
[docs/install.md](../docs/install.md) and [docs/architecture.md](../docs/architecture.md).

A web tier in one VPC: an Application Load Balancer in front of an Auto Scaling Group of instances, backed by Aurora.

```text
infra-example/
├── dev/web-demo/                one root, one state
│   ├── main.tf                  reads common.yaml and inputs.yaml into locals; preconditions (required keys, folder name, prod policy)
│   ├── network.tf               VPC and the three security groups (load balancer, app, database)
│   ├── database.tf              Aurora
│   ├── load_balancer.tf         Application Load Balancer, target group, listener
│   ├── web.tf                   instance role, launch template, Auto Scaling Group
│   ├── outputs.tf               DNS name, endpoints, secret ARN, summary
│   ├── inputs.yaml              the values of this environment
│   └── web-user-data.sh.tftpl   boot script of the web instances (placeholder web server with /health)
└── prod/web-demo/               the same files (the compute file is `ec2.tf`), production values
```

The `.tf` files are the same in both roots. What differs between environments is data (`inputs.yaml`), plus the production policy that
`main.tf` enforces.

## Where each setting lives

| Setting | Where |
| --- | --- |
| Project name, state settings, AI switch, accounts | `common.yaml` at the repository root |
| Environment, owner, cost center and everything else about the environment | `inputs.yaml` (`main.tf` checks that `environment` equals the parent folder name) |
| Mandatory tags | `project` from `common.yaml` plus `environment`, `owner`, `cost_center` from `inputs.yaml` |
| AWS region | the `AWS_REGION` secret (there is no provider block to copy) |
| Terraform version | `.terraform-version` at the root; `>= 1.11` is needed for the S3 native lock |
| Remote state | generated by the pipeline; nothing to write by hand (see [architecture](../docs/architecture.md#state)) |

## inputs.yaml

Block-style YAML only (no braces, no inline lists).

| Key | Meaning |
| --- | --- |
| `environment`, `owner`, `cost_center` | Mandatory tags; `environment` must be `dev`, `staging` or `prod` and equal the folder name |
| `ports` | `app` and `db`: defined once, used by the security groups, the target group, the database and the instances |
| `network` | `cidr_block`, optional `nat_gateway_mode` (`none` by default, `single`, `per_az`), `availability_zones`, one public and one private subnet CIDR per zone |
| `security_groups.<alb\|app\|db>` | `ingress` / `egress` rules: `description`, `port` (a number or `app`/`db`/`https`/`http`), optional `protocol`, and one of `cidr_ipv4` (`vpc` = the VPC CIDR) or `source_sg`; `alb.allow_public_ingress` permits `0.0.0.0/0` |
| `database` | `engine` (`postgresql` or `mysql`), `engine_version`, `database_name`, `instance_class`, `backup_retention_days`, `deletion_protection`, `skip_final_snapshot`, `instances`, `cluster_parameters`, optional `serverless_v2` |
| `alb` | `internal`, `deletion_protection`, `target_groups`, `listeners` (`forward`, `redirect` or `fixed_response`), optional `rules` |
| `instance_role` | `assume_role_services`, `managed_policy_arns`, `create_instance_profile`, `allow_read_db_secret` |
| `compute` | `target_group`, `instance_type`, `ami_id` (null = latest AL2023; pin it in production), volume size, `min/desired/max_size`, health check, instance refresh, `scaling_policies` |

Changing `database.engine` to `mysql` also needs a matching `engine_version` (for example `8.0.mysql_aurora.3.05.2`): the aurora module
rejects a mismatch.

## What is checked, and by whom

- **`main.tf`**, at every plan: required keys, one subnet CIDR per zone, `compute.min_size <= max_size`, and the **production policy**:
  an HTTPS listener, `nat_gateway_mode = per_az`, database deletion protection with a final snapshot, at least two database instances
  and `compute.min_size >= 2`. Because it lives in the root, it also protects an `apply` from a laptop, not only CI.
- **The modules' typed variables:** CIDRs, enums, sizes, names.
- **The reviewer** ([the checks](../docs/checks.md)): the plan (replacing a database in a protected root) and the cost increase.

## Design notes

- **Traffic is tiered by security group.** The app group accepts only from the load balancer's, the database group only from the app's.
  The reverse directions use the VPC CIDR with explicit ports, because references both ways would be a dependency cycle.
- **Egress is explicit.** No tier has allow-all egress. With the default `nat_gateway_mode: none` the app tier has no internet at all:
  use `single` so instances can install packages, or add VPC endpoints (not in this example).
- **Secrets stay out of outputs and user data.** Aurora generates the password in Secrets Manager; the instances only get the secret's
  ARN and an IAM policy to read it.
- **The state is one per environment.** Any change plans and locks the whole environment, including the database.

## Before the first apply

The first apply creates billable resources: NAT gateway (one in dev when enabled, one per zone in prod), load balancer, Aurora and EC2.
Dev is sized to be cheap but is not free: destroy it when idle. Set a real `database.engine_version` in `inputs.yaml`
(`aws rds describe-db-engine-versions --engine aurora-postgresql --query 'DBEngineVersions[].EngineVersion'`), the prod certificate
ARN in `alb.listeners` (a placeholder today) and a pinned `compute.ami_id` in prod.

| Failure | Effect | Mitigation |
| --- | --- | --- |
| Zone outage | Half of web and database capacity gone | Two zones; prod: at least two web and two database instances, NAT per zone |
| Writer failure | Failover to a reader | Prod runs two database instances |
| Bad launch template version | Rolling refresh stalls | `min_healthy_percentage`; review the plan |

## Adding an environment

Copy `infra-example/dev/web-demo` to `infra-example/<environment>/web-demo`, set `environment` in `inputs.yaml` to the parent folder
name, edit the values, and add the new root under `terraform.deploy` for the branch that should apply it. The bucket and the state key
follow from the folder and the account.
