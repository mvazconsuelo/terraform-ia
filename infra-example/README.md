# infra-example

English · [Español](README.es.md)

Two example **root configurations** built from `modules/`: `dev/web-demo` and `prod/web-demo`. The reviewer and the workflows treat
them like any other root; nothing in the platform depends on these names. Setup, branches, secrets and the pipeline are in
[docs/install.md](../docs/install.md) and [docs/architecture.md](../docs/architecture.md).

`inputs.yaml` belongs to the project that builds the infrastructure, which here is this example: the modules know nothing about it. Their
variables are their contract, and the `.tf` files of the root translate `inputs.yaml` into them.

A web tier in one VPC: an Application Load Balancer in front of an Auto Scaling Group of instances, backed by Aurora.

```text
infra-example/
├── dev/web-demo/                one root, one state
│   ├── main.tf                  reads inputs.yaml and common.yaml (inputs, tags)
│   ├── network.tf               VPC and the three security groups (load balancer, app, database)
│   ├── database.tf              Aurora
│   ├── load_balancer.tf         ACM certificate, Application Load Balancer, target group, listener
│   ├── ec2.tf                   instance role, launch template, Auto Scaling Group
│   ├── data.tf                  data sources (the IAM policy the instances use to read the database secret)
│   ├── outputs.tf               DNS name, endpoints, secret ARN, summary
│   ├── inputs.yaml              the values of this environment
│   └── web-user-data.sh.tftpl   boot script of the web instances (placeholder web server with /health)
└── prod/web-demo/               the same files, production values
```

The `.tf` files are the same in both roots. What differs between environments is data (`inputs.yaml`), plus the production policy that
the reviewer enforces (`POLICY-001`).

## Where each setting lives

| Setting | Where |
| --- | --- |
| Project name, environments (and their roots), state settings, AI switch | `common.yaml` at the repository root |
| Owner, cost center and everything else about the environment | `inputs.yaml` |
| Names of the components | a `name` in each block of `inputs.yaml`, the full physical name (`terraform-ia-dev-db`); the `.tf` only reads it |
| Mandatory tags | `owner` and `cost_center` in the `tags:` block of each root's `inputs.yaml` (each project sets its own), plus the `project` and the `environment` from `common.yaml`; `main.tf` joins them in `local.tags` and every module call passes `tags = local.tags` |
| AWS region | the `AWS_REGION` secret (there is no provider block to copy) |
| Terraform version | `.terraform-version` at the root; `>= 1.11` is needed for the S3 native lock |
| Remote state | generated by the pipeline; nothing to write by hand (see [architecture](../docs/architecture.md#state)) |

## inputs.yaml

Block-style YAML only (no braces, no inline lists).

| Key | Meaning |
| --- | --- |
| `tags` | `owner` and `cost_center`. The `project` and the `environment` are not set here: they come from `common.yaml` |
| `network` | `name`, `cidr_block`, optional `nat_gateway_mode` (`none` by default, `single`, `per_az`), `availability_zones`, one public and one private subnet CIDR per zone |
| `security_groups.<alb\|app\|db>` | `name`, `ingress` / `egress` rules: `description`, `port` (a number), optional `protocol`, and one of `cidr_ipv4` (`vpc` = the VPC CIDR) or `source_sg`; `alb.allow_public_ingress` permits `0.0.0.0/0` |
| `database` | `name`, `port`, `engine` (`postgresql` or `mysql`), `engine_version`, `database_name`, `instance_class`, `backup_retention_days`, `deletion_protection`, `skip_final_snapshot`, `instances`, `cluster_parameters`, optional `serverless_v2` |
| `certificate` | `name`, `domain_name`, `subject_alternative_names`, `zone_id` (the Route 53 zone of the domain; empty creates no validation records) |
| `alb` | `name`, `internal`, `deletion_protection`, `target_groups`, `listeners` (each with its `port`; the action is `forward`, `redirect` or `fixed_response`), optional `rules` |
| `instance_role` | `name`, `assume_role_services`, `managed_policy_arns`, `create_instance_profile`, `allow_read_db_secret` |
| `compute` | `name`, `port` (the one the instances serve), `target_group`, `instance_type`, `ami_id` (null = latest AL2023; pin it in production), volume size, `min/desired/max_size`, health check, instance refresh, `scaling_policies` |

Changing `database.engine` to `mysql` also needs a matching `engine_version` (for example `8.0.mysql_aurora.3.05.2`): the aurora module
rejects a mismatch.

## What is checked, and by whom

- **The modules' typed variables:** CIDRs, enums, sizes, names, the number of subnets per zone, the Auto Scaling Group sizes and the format of
  `tags.environment`. A module checks its own inputs, so it does so wherever it is used.
- **The reviewer** ([the checks](../docs/checks.md)), on every pull request and before anything is planned:
  - `ROOT-001` and `ROOT-002`: the root holds only its listed files, and they are identical in `dev` and `prod`.
  - `ROOT-003` and `ROOT-004`: the root is listed under an environment of `terraform.environments`, and its `tags` block has `owner` and `cost_center` and does
    not set the `project` or the `environment`.
  - `POLICY-001`: a root whose environment is a production one has an HTTPS listener, database deletion protection with a final
    snapshot, `nat_gateway_mode = per_az`, at least two database instances and `compute.min_size >= 2`. The requirements are data in
    `rules.yaml`, so another project changes them there.
  - The plan (replacing a database in a protected root) and the cost increase.

## Design notes

- **Traffic is tiered by security group.** The app group accepts only from the load balancer's, the database group only from the app's.
  The reverse directions use the VPC CIDR with explicit ports, because references both ways would be a dependency cycle.
- **Egress is explicit.** No tier has allow-all egress. With the default `nat_gateway_mode: none` the app tier has no internet at all:
  use `single` so instances can install packages, or add VPC endpoints (not in this example).
- **Secrets stay out of outputs and user data.** Aurora generates the password in Secrets Manager; the instances only get the secret's
  ARN and an IAM policy to read it.
- **The state is one per environment.** Any change plans and locks the whole environment, including the database.

## Before the first apply

The first apply creates billable resources: NAT gateway (one in dev when enabled, one per zone in prod), load balancer, Aurora and EC2.
Dev is sized to be cheap but is not free: destroy it when idle. Set a real `database.engine_version` in `inputs.yaml`
(`aws rds describe-db-engine-versions --engine aurora-postgresql --query 'DBEngineVersions[].EngineVersion'`), the `certificate` domain
and zone (`example.com` today, an example) and a pinned `compute.ami_id` in prod.

| Failure | Effect | Mitigation |
| --- | --- | --- |
| Zone outage | Half of web and database capacity gone | Two zones; prod: at least two web and two database instances, NAT per zone |
| Writer failure | Failover to a reader | Prod runs two database instances |
| Bad launch template version | Rolling refresh stalls | `min_healthy_percentage`; review the plan |

## Adding an environment

Copy `infra-example/dev/web-demo` to `infra-example/<environment>/web-demo`, edit the values, and add the new environment under `terraform.environments` in `common.yaml` with its `branch` and its `roots`. The bucket and the state key
follow from the folder and the account of its branch (a repository variable, see [Setup](../docs/install.md)).
